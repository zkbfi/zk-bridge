# GPU trial, 2026-11-01

Goal: find the GPU that proves fastest, for a dedicated prover. The owner's rule: "lets assume that the time to get the proof is of utmost importance ... dedicated, especially if we assume that we will have consistent usage is the way to go".

The trial was cut short by the owner's later instructions ("just use the prod one", "try to reduce costs wherever you can"): it moved from on-demand pods to the production serverless endpoint, ran 2 proofs per GPU instead of 3, skipped the L40S, and ran the H100 only because the GPU's share of the proof time could not be measured (see "Why the H100 was tried"). Only two GPUs produced proofs. The rest never got a running worker.

## Method

- Client: `zk-bridge-prover prove` built from the per-step timing branch (`--no-default-features`), backend `remote`, `--to stdout` only. No webhook, no transaction.
- Route `pulsechain-testnet-v4_to_sepolia`, the Sepolia light client `0x64ddc23f...6e4e`. Start head 11214944 (the head the light client stored), new head 11218176.
- Same input for every run: a local record and replay proxy in front of the public beacon API of chain 943, the chain 943 RPC and the Sepolia RPC. The responses were recorded once, before any GPU ran. Every later run read only the recording, so the light client head and the newest finalized header could not move between runs. Every proof has the same public values (SHA-256 of the hex string starts `e42926c771e046ad`).
- Every proof has 356 bytes, and `zk-bridge-prover verify` accepted each one (`{"valid":true}`) for the program key `0x000854b9b72ab6bfca191c95cb131971a17a458c2faebdd216d9dbe874eb4730`.
- Image: `ghcr.io/zkbfi/zk-bridge-prover-gpu-worker:v6`. It reports no worker timings (`worker_timings=none`), so `remote_ms` holds the whole request: the native run on the worker, the SP1 proof (core, compression, Groth16 wrap) and the network.

## Recommendation

For a dedicated prover today, take the **RTX 5090**: a warm proof in about 36 s end to end, the fastest measured, at $1.19 per hour ($857 per month). It ran when the 4090 and the H100 could not be had at all, and for a dedicated machine, getting one counts as much as speed.

What is still open:

- How much of the 36 s is GPU work and how much is the Groth16 wrap on the processor. The v7 image reports `worker_prove_ms` and the host CPU. Run one warm proof on v7 before you pay for a faster GPU. If the processor part dominates, an H100 ($3.99 per hour, 3.4 times the price) cannot help much, and a host with more or faster cores matters more than the GPU.
- The H100 and the 4090 were not measured. Older figures in `docs/gpu-prover.md` (4090, image v3, older program) show a warm proof of about 27 s, but with another program, so they do not compare.

## Production endpoint after the trial

The endpoint `43nsvfb8svkosr` is back to its settings from before the trial: the same nine GPU types in the same order, workers min 0, max 1, idle timeout 60 s, the same template. Its version number went from 9 to 18. The template `hsj330cqpf` is on `ghcr.io/zkbfi/zk-bridge-prover-gpu-worker:v6`. v7 (`@sha256:b7786a1b...aecd`) was on the template for one try and was taken off when its worker did not start.

The last worker of the endpoint before the trial was a MIG slice, `NVIDIA RTX PRO 6000 Blackwell Server Edition MIG 2g.48gb`. The section "GPU type requirement" says no MIG type may serve this endpoint. The type list names only whole GPUs, but RunPod's pool for `NVIDIA RTX PRO 6000 Blackwell Server Edition` (`BLACKWELL_96`) still handed out a MIG slice. Remove that type, or check the pool, before you rely on the list.

## Follow-up: RTX 3090 and RTX A5000 (same day, for a home prover)

The question was whether a used RTX 3090 is a good home prover. Both runs used the production endpoint, the same replayed input and image v6, with one GPU type at a time and `workersMin 1`.

| GPU | Result |
|---|---|
| RTX 3090 | Unavailable. In 10 minutes no RTX 3090 worker was assigned. RunPod assigned MIG slices instead (`RTX PRO 6000 Blackwell Server Edition MIG 2g.48gb`, which was terminated a few seconds after it started, and `MIG 1g.24gb`, which never started), although the type list named only `NVIDIA GeForce RTX 3090`. No proof was made. |
| RTX A5000 | Unavailable. In about 10 minutes no worker was assigned, and the run was stopped there. No proof was made. |

Spend of the follow-up: about $0.001 (one MIG worker that ran for a few seconds). No RTX 3090 or A5000 worker ran, so the trial says nothing about their proof time.

RunPod handed out a MIG slice for a list that named only the RTX 3090. A MIG 1g.24gb slice ran out of host memory in the Groth16 step before (see "GPU type requirement" in `docs/gpu-prover.md`). Naming whole GPU types does not keep MIG slices off this endpoint.

The endpoint was restored afterwards (same settings as the first snapshot, version 21, template on `:v6`), and the API listed no pod.
